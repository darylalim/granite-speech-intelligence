# CLAUDE.md

## Project Overview

Streamlit application for English speech transcription using IBM Granite Speech 5.0 TurboCTC on Apple Silicon with MLX, with VAD-based audio segmentation and timestamps, plus optional transcript analysis — a summary card and a yes/no question board — from Granite 4.2 3B through `mlx-lm`. English only: the speech model is an encoder-only greedy-CTC recogniser with no prompt and no decoder, so there is no translation, no source-language choice and no keyword biasing. Analysis is off by default, reads the finished transcript and never re-transcribes; both models run on the machine, and nothing leaves it. How the analysis was planned, measured and decided is in `docs/PLAN.md`; this file describes what shipped, and wins where the two disagree.

## Setup

```bash
uv sync
uv run streamlit run streamlit_app.py
```

Reload-on-save is off in `.streamlit/config.toml` (see Configuration); while editing the app, add `--server.fileWatcherType auto` to get it back.

No system FFmpeg is needed: audio is decoded by PyAV (`av`), whose wheel bundles FFmpeg. It used to go through `torchaudio.load` → `torchcodec`, which `dlopen`s whatever FFmpeg Homebrew has installed — see the `av` entry under Dependencies for why that was retired.

## Git

- **Conventional commits, with scopes** — `type(scope): imperative subject`, lowercase, no trailing period. Types in use: `feat`, `fix`, `perf`, `refactor`, `chore`, `docs`, `test`; scopes: `ci`, `vad`, `pipeline`, `hooks`, `ui`, `deps`. Not cosmetic — the `release` job pipes `git log --format='* %s (%h)'` straight into the published notes, so a malformed subject ships into a GitHub release rather than into a diff nobody reads. The one subject that must *not* ship is the version bump's, and the job drops it by exact spelling — `sed '/^\* chore: bump version to [^ ]* ([0-9a-f]*)$/d'` over the formatted lines — so a bump commit is always `chore: bump version to <version>` and nothing more. A scoped or `build:`-typed bump lands in the notes again, as every CI-published release's did before the filter (v0.12.0–v0.14.0's were removed by hand with `gh release edit`, which also gave them the titles they lacked; v0.11.0's notes were hand-written; v0.15.0 was the first to publish with its title and notes right and untouched); and a bump that also did something (`… to 0.2.0 and add project description`, 21b5435) is deliberately *not* filtered either — it surfaces so the change it carried gets listed, where a prefix match would have dropped both. The filter runs over the formatted line rather than through `git log --grep` because `--grep` tests every line of the message: a commit merely quoting the bump subject at the start of a body line would vanish from the notes.
- **Work is committed on a branch for review, never on `main`, and lands by fast-forward only — no merge commits** (217 commits, zero merges as of 2026-10-20). Branch before a task's first commit, commit there and stop: don't merge, don't push, and say which branch holds the work (`git log main..<branch>`, `git diff main...<branch>`). The user reviews and brings it in with `git merge --ff-only <branch>`, rebasing first if `main` has moved. Fast-forward is load-bearing, not taste: the release notes are the commit subjects since the last tag, so a merge commit's `Merge branch …` subject would ship in them, and pushing `main` with a `version` bump publishes a release outright — which is why the review happens before anything reaches `main`. Reviews are local, not PRs, so `gh --generate-notes` stays unusable in the release job (it builds from merged PRs; see its comment in `ci.yml`), and CI does not run on a review branch (`on:` is `push` to `main` plus `pull_request`) — the local checks are the only gate before the merge, and the Stop hook only sees uncommitted changes, so hand-run all three on the branch before handing it over. Leave every `git push` to the user.

## Permissions, Hooks & CI

- `.claude/settings.json` **permissions**: `"deny": ["Edit(uv.lock)"]` — the lock is generated and must change only via uv (`uv add`/`remove`/`lock`/`sync`); a hand-edit desyncs it from `pyproject.toml` and breaks resolution. This replaced a PreToolUse hook that did the same check in bash: the rule needs no subprocess per edit, has no `jq` dependency to fail open on, and also covers file commands Claude Code recognises in Bash (`sed -i`, `cat >`) that the hook's `Edit|Write` matcher missed. It must be spelled `Edit(...)`, not `Write(...)` — path rules are consulted for `Edit(path)`/`Read(path)` only, and an `Edit` rule already covers Write and NotebookEdit; a `Write(uv.lock)` rule would be accepted, never consulted, and warn at startup. Running `uv` itself is unaffected: deny rules don't reach subprocesses that write files themselves.
- `.claude/` hooks: a **Stop hook** (`check-on-stop.sh`) auto-runs `ruff check` + `ty check` + `pytest -q` and blocks turn completion on failure — no need to hand-run them at end of turn (~5.5s: ruff 0.03s, ty 0.95s, pytest 4.6s). Two holes worth knowing, both deliberate: the gate is `git status --porcelain`, so it sees **uncommitted** `.py` changes only and `.py` edits committed earlier in the turn leave a clean tree and go unchecked — hand-run the three there; and `stop_hook_active` caps it at one block per turn, so a second stop goes through with the checks still red. It is a prompt to fix, not a wall. A **PostToolUse hook** (`ruff-on-edit.sh`) auto-`ruff format`s edited `.py` files (format only, not `check --fix`). The two don't overlap by design — format is idempotent and safe after every edit, lint is order-dependent and gated once when the code is stable.
- CI + releases (`.github/workflows/ci.yml`): a `check` job — `uv sync --locked`, `ruff check`, `ruff format --check`, `ty check`, `pytest` — on macOS across Python **3.12 and 3.13**, then a `release` job. **Read the file for the rationale**: its comments already answer why macOS is mandatory rather than preferred, why there is deliberately no `brew install ffmpeg` step any more, why `release` reads the version instead of diffing it, and why the notes come from `git log`. `ruff format --check .` there covers every `.py` file in the repo (`evals/` and `tests/llm_fakes.py` included) plus three Markdown files: since ruff 0.16.0 the formatter formats ```python fences in Markdown by default, so `CLAUDE.md`, `README.md` and `docs/PLAN.md` are in the run (none has a fence today — the string appears in their prose only; ```bash fences are ignored) — and neither hook can see a fence, so an unformatted Python fence in any of them is caught only in CI. Three things the YAML does *not* say, and a session would otherwise undo:
  - **Bumping `version` in `pyproject.toml` is the entire release action.** Push it to main and CI tags `v<version>`, writes notes from the commit subjects since the last tag — minus any bump commit, filtered by its exact `chore: bump version to <version>` subject (see Git) — and publishes, titled `v<version>` explicitly: `gh release create` stores no title unless given one, and GitHub renders an untitled release as `<tag>: <subject of the tagged commit>`, i.e. the bump subject again, in the repo sidebar and the releases list. Idempotent, so a failed run is fixed by re-running it; but idempotent means *already-released tags are left alone*, so a change to the notes format reaches an already-published release only through `gh release edit`, never by re-running the job. Releases publish outright — add `--draft` to `gh release create` if they should instead wait for a hand-edit.
  - Steps **in the `check` job** are unnamed on purpose — GitHub labels an unnamed step with its own command, so `Run uv run ruff check .` beats any `name:` paraphrase on failure. Don't re-add them. The `release` job's one step keeps its `name:` because its body is a 40-odd-line script, where the auto-label would be the whole thing.
  - Both matrix legs earn their place: 3.12 is the `requires-python` floor and ty's target, 3.13 is what a fresh `uv sync` resolves to — and `fail-fast: false` stops a 3.12 failure from cancelling 3.13 and hiding a 3.13-only break.

## Dependencies

- `mlx-audio` — MLX-based speech model loading and inference (Apple Silicon). Declared as `mlx-audio>=0.5.1` (locked at 0.6.1), and the floor is load-bearing: `granite_speech5_ctc` entered `mlx_audio.stt.utils.MODEL_REMAPPING` in 0.5.1 and is absent from 0.5.0 and the whole 0.4.x line, so an older resolution would pass `uv sync` and then fail inside `load_model` on an unknown `model_type`. The 0.5.x line also made `mlx-lm` an optional extra, so `mlx-lm` dropped out of `uv.lock` until it was declared directly (see below). `sentencepiece` dropped out with it and came back in 0.6.x as a direct requirement of `mlx-audio` itself; the app does not use it either (the TurboCTC port reads `tokenizer.json`). The 0.5.5 → 0.6.1 upgrade left the `granite_speech5_ctc` port byte-identical
- `mlx-lm` — declared `mlx-lm>=0.32.2` (locked at 0.32.2) for transcript analysis with Granite 4.2 3B (`docs/PLAN.md`, Track B; the 3B replaced the 8B at B4); imported by `streamlit_app.py` since B5 (`load` as `_load_llm`, `generate_step`, `make_prompt_cache`/`trim_prompt_cache`, `make_sampler`) for the analysis functions under Functions, which the UI drives since B7. The floor is the release the plan's API notes (`load`, `generate_step`, the prompt-cache helpers, `mlx_lm.models.granite`) were checked against. Adding it brought nothing else into `uv.lock`: all seven of its requirements (`jinja2`, `mlx`, `numpy`, `protobuf`, `pyyaml`, `sentencepiece`, `transformers`) were already there via `mlx-audio`. `load` defaults `trust_remote_code=False`, and the app must never pass `True`. Beyond those public functions the analysis leans on exactly one cache attribute, `KVCache.offset`, which sets the trim back to the prefix after a summary (the cache can run one token past what the loop consumed); the tiny-Granite contract tests exercise it, so an upstream rename fails CI rather than a summary
- `mlx` — **not declared in `pyproject.toml`**; arrives transitively via `mlx-audio`, yet `streamlit_app.py` imports it directly — `mlx.core` and `mlx.nn` at module scope for the batched VAD path. The speech model is driven purely through `mlx_audio`'s public `generate()` and has no LLM decoder to sample from, so `mlx-lm` (declared, above) is not imported by the speech path. An `mlx-audio` release that stops pulling `mlx` in breaks the app with an `ImportError` at import time rather than a resolution error at `uv sync`; `uv add mlx` is the fix if that ever bites. `import mlx.core` needs no `# ty: ignore` any more: mlx 0.32.0 shipped `py.typed` without `mlx/core/*.pyi`, so ty resolved the package but not the compiled `core` extension and the import carried `# ty: ignore[unresolved-import]`; 0.32.2 ships the stubs again (still shipped in 0.32.4), and ty flags a leftover suppression as `unused-ignore-comment`. With the stubs, `array.item()` is typed `scalar` (`bool | int | float | complex`), so `float(x.item())` is an `invalid-argument-type` — take a scalar array to Python with `float(x)` (`array.__float__`), which is what the two VAD-equivalence tests do. If a future mlx drops the stubs again, the suppression goes back on the import line in `streamlit_app.py` and `tests/test_streamlit_app.py`
- `huggingface_hub` — also **not declared**, transitive via `mlx-audio`. Since B5 `streamlit_app.py` imports it at module scope: `errors.LocalEntryNotFoundError`, which `load_llm` maps to the offline error, and `constants.HF_HUB_CACHE`, which the disk-full message names. `tests/test_streamlit_app.py` also imports `try_to_load_from_cache` for the real-weights smoke tests' cache gate (see Tests). Same category as `mlx`: an upstream release that stops pulling it in fails the app at import time, not at `uv sync`; `uv add huggingface_hub` is the fix
- `torch` — tensor operations (waveform handling, the PyTorch VAD fallback)
- `av` (PyAV) — audio decoding for the whole pipeline (`_decode_audio`) and the header-only duration read (`audio_duration_seconds`). Declared `av>=19.0.0` — the floor is the tag-decoding change described under `_open_container`. Chosen because its wheel **bundles FFmpeg**: the previous decoder, `torchaudio.load` → `torchcodec`, `dlopen`s the FFmpeg that Homebrew has installed, and that broke twice in one week — Homebrew moved `ffmpeg` to 9.0 while torchcodec 0.15 shipped loaders for 4–8 only, and torchcodec 0.16 added the 9 loader but dropped the `/opt/homebrew/opt/ffmpeg/lib` rpath from its dylibs, so on Apple Silicon it finds no FFmpeg at all (upstream: meta-pytorch/torchcodec #1631, fixed by #1632 after 0.16.0 shipped; the rpath it dropped was the one #1152 added to close #570). Neither is fixable from inside the process — dyld reads its search paths at launch, so `os.environ["DYLD_FALLBACK_LIBRARY_PATH"]` and `ctypes` preloading were both tried and both fail — and the alternatives (a versioned `ffmpeg@8` plus a symlink into Homebrew's `opt/`, or a `DYLD_*` variable on every launch command) are not instructions to give users. A fresh `brew install ffmpeg` produced a crash at import; with PyAV there is nothing to install. Decode is verified bit-exact against the WAV fixture's own PCM (`test_wav_decodes_bit_exactly`), and three review-found regressions are pinned by containers built in-test with PyAV's own encoders — `latin1_tagged_wav` (an ANSI RIFF INFO tag must neither fail the load nor blank the duration), `two_track_mkv` (the `default`-flagged second track wins over the first, for both decode and duration) and `undecodable_mkv` (an mp3 track relabelled as AC-4 raises the readable `no decoder is available` error)
- `torchaudio` — the pure-torch resampler only (`torchaudio.functional.resample`, to `SAMPLE_RATE` after the mono downmix). It neither imports nor depends on `torchcodec` (verified: `torchcodec` is absent from `uv.lock` and from `sys.modules` after `import torchaudio`), which is what lets the decoder change leave the resample numerically identical
- `silero-vad` — Voice Activity Detection; supplies the PyTorch fallback checkpoint (its 16 kHz weights are bit-exact with `MLX_VAD_REPO`). Pinned `silero-vad==6.2.3` (moved from 6.2.1 on 2026-10-20), and the pin is exact on purpose. This checkpoint is the other half of the bit-exact pair `MLX_VAD_REVISION` freezes, and 6.1 and 5.x ship different weights; the `.jit` is byte-identical across 6.2.1, 6.2.2 and 6.2.3 (sha256 `e1122837…`), and `test_both_backends_agree_on_real_audio` passed on 6.2.3, whose `get_speech_timestamps` was refactored to delegate to a new `get_speech_timestamps_from_probs`. 6.2.2 was skipped: it declares `torchaudio<2.10` — its only torchaudio users are its own `read_audio`/`save_audio`, which the app never calls — and torchaudio 2.9.1's wheel pins `torch==2.9.1`, so inheriting it drags torch from 2.14 back to 2.9.1 (exactly what `uv lock --upgrade` did on 2026-09-21 until the bound went in); it also imports `onnxruntime` at package import (`silero_vad/__init__` → `sequence_vad`) while declaring it only as an extra, so `import silero_vad` fails outright here. 6.2.3 fixed both — torchaudio (and torchcodec) moved to the `audio`/`codec` extras and are imported lazily by the I/O helpers alone, and the sequence path's `onnxruntime` import is deferred (PEP 562) — and with it torch stays at 2.14. Keep the pin exact rather than a floor, so `uv lock --upgrade` never picks up a later release that reintroduces either problem and silently downgrades torch again; moving it is a deliberate edit, made after the same checks
- `streamlit` — web user interface. Declared `streamlit>=1.51.0` in `dependencies` — `st.space` landed in 1.51.0 and is the newest API the layout uses (horizontal containers and `width=` on `st.container`/`st.button` are 1.48.0; every call the app makes was checked against a scratch 1.51.0 install). It was `>=1.52.0` for `text_alignment=` on `st.title`/`st.markdown`, which the sidebar layout removed — and `streamlit>=1.64.0` in the `dev` group (locked at 1.66.0): the higher floor is the tests', not the app's — `AppTest.session_state` became an iterable dict-like wrapper in 1.64.0 (streamlit#16897) and `tests/test_app_ui.py` iterates it for the single-slot `_duration` check, where on 1.63.0 and below the comprehension raises `KeyError` from the legacy `__getitem__(0)` iteration. uv resolves both groups together, so the split changes nothing in the lock
- `ruff` — linting/formatting (dev)
- `ty` — type checking (dev)
- `pytest` — testing (dev)

## Configuration

`pyproject.toml` — ruff isort (`combine-as-imports`), ty (`python-version = "3.12"`), and pytest (`pythonpath = ["."]`). That last one is load-bearing: there is no `conftest.py` and no `[build-system]`, so the project is never installed as a package and pytest's prepend mode puts `tests/` — not the repo root — on `sys.path`. It is the only reason `from streamlit_app import ...` resolves; don't "clean it up" into a `conftest.py`.

`.streamlit/config.toml` — `[server] maxUploadSize`, `address = "localhost"` and `fileWatcherType = "none"`, `[browser] gatherUsageStats = false`, plus a custom `[theme]`. The watcher is off because it probes every module in `sys.modules` (`hasattr(m, "__path__")`), and transformers' lazy loader answers that by importing image processors that need `torchvision`, which is not installed — about 100 `ModuleNotFoundError` tracebacks in the console per browser session (counted 2026-10-20: 105 with the watcher, 0 without; the transcript is identical either way). It predates the 2026-10-20 dependency upgrade (204 on the previous lock for two sessions), and `transformers` arrives only via `mlx-audio`, so there is no import to remove. Installing `torchvision` to quiet a log, or raising the log level and hiding the VAD-fallback warning with it, were rejected. The menu's "Auto rerun" toggle stays visible and is inert without a watcher. The two security keys keep "nothing leaves the machine" true in both directions. Unset, `server.address` makes the server listen on every interface: verified 2026-10-17, it logged `started on :::8599` and printed Network and External URLs, so anyone on the same Wi-Fi could upload files for FFmpeg to parse and run the models. With the key set it logs `started on localhost:8599`, `lsof` shows `127.0.0.1:8599` only, and the LAN address refuses connections. `gatherUsageStats` defaults to on, which sends Streamlit's own usage statistics out of an app whose design is that nothing leaves the machine. The theme: **IBM Carbon**, Gray 100 tokens for dark and White tokens for light, with one accent, Blue 60 `#0f62fe`, declared once under `[theme]` because the band where white button text clears 4.5:1 does not depend on the surface. Sixteen keys, every colour line naming its Carbon token and the ratio that chose it; anything unset inherits the mode's built-in value on purpose (no green — nothing renders `st.success`; no chart, dataframe, metric or code keys; no fonts — the bundled Source Sans 3 needs no fetch and no `static/` dir, and this is an offline app; `linkUnderline` and `showSidebarBorder` at default). Four decisions worth knowing before touching it. **Dark `textColor` is Gray 20 `#e0e0e0`, not `$text-primary` `#f4f4f4`**: 13.7:1 on the page instead of 16.5:1, because the transcript is 200 lines of lowercase text and the 12–14:1 band reads better over that length; captions (`textColor` at 60% opacity over their surface) still clear 5:1. **The selected tab label is 3.6:1 in dark by construction** — Streamlit paints it in `primaryColor` as 14 px text and paints primary buttons white-on-`primaryColor`, and no colour is both ≥ 4.5:1 under white and ≥ 4.5:1 as text on near-black, so Blue 60 takes the button's side (5.0:1) and the 2 px indicator carries selection; don't "fix" the tab by brightening the blue, it breaks the button (stock fails the other way: 5.7 tab, 3.3 button, and the removed theme's Blue 50 was 3.35:1 under white). **Alerts are keyed per mode by measurement**: `redColor` in both (Streamlit derives the error text as `redColor` lightened/darkened 15% when only that is set — 6.75:1 dark, 7.2:1 light, against stock's 4.8 / 4.6 on these pages; the same derived tone paints the recorder's recording pulse), one light `yellowTextColor` for the >30-minute warning (7.7:1 on the stock tint against 4.7), and no `yellowColor`, because in dark it lowers a passing pair and in light it derives to 2.8:1 and needs a second key to repair. **`baseRadius = "none"` and `showWidgetBorder = true`** are the Carbon identity: square buttons, fields, card, alerts and toast (the toggle keeps `radii.full`, and the browser-drawn audio player stays rounded — one native control, accepted), and the border is the only thing that gives the dropzone and recorder an edge, which is also why `borderColor` is `$border-subtle-01` (`#525252` / `#c6c6c6`) and not `-00` (1.3:1 on the layer, invisible). The dark toggle-off track is `borderColor` on the sidebar at 1.94:1 (stock 1.88), and the knob carries the state; the light rims are fainter still — 1.55:1 on the layer, 1.71:1 on the page — which is Carbon's hairline by design, and the stock derived light border is 1.45:1. **Both `[theme.light]` and `[theme.dark]` must carry values.** A custom theme that sets only top-level `[theme]` keys locks the app to a single mode, and the appearance section does not merely lose entries — it **disappears from the menu entirely**, leaving no way back. Verified by A/B on 1.61.1 and again on 1.64.0, and the menu rechecked present on 1.66.0 (2026-10-20) (`--theme.primaryColor` alone → no appearance section, app pinned to light despite a dark system setting; no flag → System/Light/Dark present). The frontend builds that section from the available-themes list and early-returns `[]` at length ≤ 1, which is what a top-level-only theme collapses it to. It keeps the menu as soon as *either* sub-table carries a value — the three entries it then emits are the bundle's `Custom Theme Light` / `Custom Theme Dark` / `Custom Theme Auto`, with the missing mode derived from `[theme]` plus its `base` (`--theme.light.primaryColor` alone → System/Light/Dark present, verified on 1.64.0) — but `test_config_theme_defines_both_palettes` demands **both** sub-palettes regardless, because a mode that is only derived is a mode nobody reviewed. `base` is valid only under `[theme]` and is not set: the sub-tables already inherit their own mode's built-in palette, and a `base` line inside one is logged as invalid at startup and ignored. (History: an earlier Carbon-inspired theme was removed in b6e26ab for being half-done — its dark Blue 50 failed white-text contrast and its light borders were 1.3:1 — and the app ran on Streamlit's built-in palettes until this one; every value here was measured against the surface it paints.) The explanatory comment sits **above** `[server]`, not under it: TOML scoping is positional, so a theme key added beneath a trailing comment would silently become `server.<key>`; new theme options go under the `[theme]` headers.

## Architecture

`streamlit_app.py` — single-file app.

### Functions

- `is_video` — predicate by extension, drives `st.video` vs `st.audio` preview
- `select_source` — decides which input tab supplies the audio, **most recently touched wins**, and it is the reason the app does not say `audio_file = uploaded or recorded`. `st.tabs` keeps both tabs mounted, so the uploader and the recorder can hold a value at the same time, and `or` settled that permanently in the upload's favour: a recording made after an upload landed in the widget and did nothing, the caption kept naming the file, Transcribe kept using it, `_last_input_key` never moved, and the only way out was going back to Upload and clearing. Takes the two `file_id`s plus the `SourceState` carried in `st.session_state["_source"]` — `(upload_id, record_id, active)` — and returns the next one: whichever id changed this rerun becomes `active`, an unchanged pair keeps the standing choice, and an `active` source that has since been cleared hands over to the other (or to `None`). Pure and keyed on ids rather than files, so `test_select_source` walks the whole truth table in eleven parametrized cases without a script run. Two earlier options were rejected: a caption explaining the precedence (it narrates the dead end rather than removing it) and letting the visible tab pick (`st.tabs(..., on_change="rerun")` plus `upload_tab.open`, which makes merely *peeking* at Record set `audio_file` to `None`, move `_last_input_key` and drop the card). **`from_upload` — not `uploaded` — is what the filename caption and the download stem key on**: with both widgets holding a value `uploaded` stays truthy even when the recording is the source, so keying on it would caption and name the file after an upload the transcript did not come from (`test_the_recording_supplies_the_download_stem_when_it_is_the_source`)
- `format_timestamp` — formats seconds to `M:SS` or `H:MM:SS`
- `audio_duration_seconds` — returns clip duration from the container headers via `_open_container` (no frame decoded): the best audio stream's (`_best_audio_stream`) `duration * time_base`, else the container's `duration / av.time_base` (microseconds), else `None`; also `None` for unparseable bytes, a container with no audio stream, or a non-positive figure. Used to gate the Run button when VAD is off on long audio (threshold `MAX_VAD_OFF_DURATION_S = 1800`, thirty minutes).
- `silero_vad` — runs Silero VAD on waveform, returns `(start, end)` tuples in seconds. Dispatches between two backends over the **same checkpoint**: `_mlx_vad_spans` (MLX, default) and `_torch_vad_spans` (the `silero-vad` PyPI model, fallback). A `torch.nn.Module` routes straight to PyTorch; anything else takes MLX inside a `try/except` that warns (`RuntimeWarning`) and falls back. **Non-16 kHz audio always goes to PyTorch**: the v6 conversion ships no 8 kHz weights, but `mlx_audio` builds that branch anyway and loads non-strictly, so calling it at 8 kHz runs randomly initialised layers and returns confident nonsense instead of failing (verified: loaded 8k weights have std 0.041 vs the trained 0.951)
- `_supports_mlx_vad` — probe over the `mlx_audio` surface the fast path drives (`vad_16k` + its conv/lstm submodules, `_MLX_VAD_BRANCH_CONFIG_ATTRS`, `model.dtype`, the model-level threshold config, and the private `_probs_to_timestamps`). **This is the only place the app still reaches into `mlx_audio` internals** — the speech model is driven through its public `generate()` alone (see the hoist note under `run_pipeline`) — so it is also the reference pattern for any future probe: checked at load time, with the `try/except` in `silero_vad` covering the signature changes `hasattr` cannot see. **Beyond names it also checks two config *values*:** `chunk_size` and `context_size` must equal `VAD_CHUNK_SAMPLES`/`VAD_CONTEXT_SAMPLES`. The revision pin freezes the repo's `config.json` but *not* `mlx_audio`'s `BranchConfig` defaults, which fill in any field the config omits — so a dependency upgrade can still move the framing. Neither this path nor `mlx_audio`'s own `_probs_to_timestamps` (which hardcodes a 512-sample stride) could serve different framing, and getting it wrong produces plausible garbage rather than an error, so refuse instead
- `_mlx_vad_windows` — one `(context + chunk)` window per 512-sample decision chunk, framed exactly as `mlx_audio`'s streaming loop does but via `mx.as_strided`, so the 64-sample overlaps stay a view rather than a 12%-larger copy. Pads both edges in a single `mx.pad`: padding then concatenating the context would allocate two full copies of the waveform, which on a 500 MB upload is a lot of transient memory for a function whose whole purpose is avoiding a copy
- `_mlx_vad_probabilities` — per-chunk speech probabilities with the encoder batched across chunks. The STFT + conv encoder is stateless per chunk (it only ever sees that chunk's 576-sample window), so it runs on a whole batch at once; only the LSTM is sequential, and `nn.LSTM` unrolls a full `(1, T, 128)` sequence in one graph, so carrying `(hidden, cell)` across batches reproduces chunk-by-chunk stepping exactly. One model call per 32 ms of audio becomes one per ~65s. **Measured 2.9–3.5× faster than PyTorch** across 10s–15min, with max |Δp| of 2.5e-06 over 9375 chunks, zero decisions flipped at threshold, and byte-identical spans. Note `mlx_audio`'s own `get_speech_timestamps` is *slower* than PyTorch here (0.66×) — at 309K parameters the per-call dispatch cost dominates the arithmetic, so call count is the only lever, and that is the whole reason this exists rather than using the library method. Guards its own core assumption: the batch axis is reused as the LSTM's sequence axis, which holds **only** while the conv stack collapses each window to one frame. Different STFT framing leaves more (`hop_length=64` measured at 2), and `x[:, 0, :]` would silently drop the rest where the reference averages them — so a frame count other than 1 raises and the caller falls back. A 256 ms noisy-OR "unified" mode (the v6 repo's `example_256ms.py`) was evaluated and rejected: same speed as batching (0.96–1.13×) but it flips 10.1% of chunk decisions, shifts every boundary up to 320 ms, and inflates detected speech ~13% — noisy-OR is one-sided by construction, so the error is systematic, not noise
- `_split_long_segment` — splits an over-long span into equal parts each within the cap (equal parts, not cap-sized chunks plus a remainder, so with a 10s cap a 30.1s span becomes 3 × ~10s rather than 2 × 15s + a 0.1s sliver that would transcribe to nothing). Backs the part count off rather than emit parts under `MIN_SEGMENT_DURATION_S` (20s): every forced split lands mid-utterance and costs a little accuracy (the WER series is under Languages), so a span only modestly over the 30s cap is left whole rather than halved — buffering pushes a natural 30.0s span to 30.6s, which would otherwise become 2 × 15.3s. With the floor above half the cap, spans under 2 × floor (40s) stay one part and only longer ones split. The floor is clamped to `max_duration` so a caller passing a cap below it still gets a split
- `get_speech_segments` — post-processes VAD output with buffering, merging, and a `max_segment_duration` cap (default `MAX_SEGMENT_DURATION_S`, 30s). Merging across sub-`min_gap` gaps stops at the cap, and any span still over it — an unbroken VAD span, or the no-speech full-audio fallback — is split by `_split_long_segment`. Without the cap, continuous speech (podcast, lecture, dictation) merged into one unbounded segment — which this model would transcribe fine (see Languages), but as a single timestamp line spanning the whole clip; the cap is what keeps timestamps readable. When the cap **refuses** a merge, the new segment's start is clamped to the previous segment's end (and skipped entirely if wholly covered): the 0.3s start/end buffers make consecutive spans overlap by `0.6 - gap` — up to 0.6s when the VAD spans abut — and merging used to absorb that unconditionally because a negative gap always satisfies the `min_gap` test. (`min_gap = 0.5` is a different quantity: it gates the merge on the *already buffered* gap, so the raw gap it admits is 1.1s.) The cap is what first made the overlap reachable — unclamped it re-transcribed up to 0.6s at every boundary and emitted timestamps that ran backwards
- `_spans_in_seconds` — shared sample-offset → seconds tail for both backends, so the two paths cannot drift apart on a conversion detail that would break their interchangeability
- `_torch_vad_model` — `@st.cache_resource`-wrapped `load_silero_vad()`, used by every fallback site. `load_silero_vad` is **not** memoised (it re-runs `torch.jit.load` per call), so calling it inline would re-deserialise the model on every pipeline run of a session that permanently falls back, and leave a second copy resident alongside whatever `load_vad_model` cached. That `torch.jit.load` is the app's only TorchScript call, and on torch ≥ 2.14 it emits `FutureWarning: torch.jit.load is deprecated. Please switch to torch.export.` (2.10–2.13 emitted the same text as a `DeprecationWarning`, which pytest already displayed — the two tests that load the PyTorch checkpoint each raise it once: the VAD-on UI run under `_offline_mlx_vad()`, and `test_both_backends_agree_on_real_audio`, which calls `load_silero_vad()` directly to compare the backends. Those same two tests also raise silero-vad's own `DeprecationWarning: path is deprecated. Use files() instead.` from `importlib.resources.path` in `silero_vad/model.py`, which makes `pytest -q` report 4 warnings on the project's Python 3.12 venv (counted 2026-10-20); the Streamlit console shows it only when the MLX VAD load fails, since the MLX path never touches `torch.jit`). No torch release names a removal version (pytorch/pytorch#189914 calls the deprecation-to-error step paused). Don't filter it: the checkpoint is `silero-vad`'s `.jit` file, so there is nothing here to migrate — if TorchScript loading ever goes, the fallback needs another loader — the wheel ships no non-JIT torch path (its `silero_vad_16k.safetensors` serves only an unwired tinygrad module), though the MLX repo's weights are bit-exact with the `.jit` ones
- `load_vad_model` — cached VAD loader. Loads `MLX_VAD_REPO` and degrades to `_torch_vad_model()` — never `load_silero_vad()` inline, for the memoisation reason above — on either failure mode — the repo not resolving (offline, renamed) or `_supports_mlx_vad` rejecting what came back — warning in both cases, since the PyTorch path is correct but ~3× slower and a silent downgrade would be invisible until someone benchmarked it. `MLX_VAD_REVISION` pins the repo, for a **different reason** than `MODEL_REVISION`. That one guards reproducibility (a retrained checkpoint would still load strictly and decode without complaint — see `load_model`); this repo is org-maintained too, but `mlx_audio`'s VAD loader takes `strict=False` and *cannot* do otherwise — the v6 conversion legitimately ships no `vad_8k.*` keys, so a strict load would reject it outright. Non-strict loading means renamed `vad_16k.*` keys would leave those layers randomly initialised, and the model would still build, still pass `_supports_mlx_vad`, still run clean, and return confident nonsense. That is the same silent-garbage mechanism documented for the 8 kHz branch, and a content hash is the only thing that rules it out. A bad hash is safe: the load 404s, warns, and falls back to PyTorch. Cold start regresses (0.590s vs 0.027s), so on a first run under ~25s of audio the MLX path is net slower; behind `@st.cache_resource` that is once per session
- `limit_mlx_cache` — `@st.cache_resource`-wrapped `mx.set_cache_limit(MLX_CACHE_LIMIT_BYTES)`. The limit is process-global, so the cache is what makes it once per process rather than once per rerun; `main()` calls it after the decode and before `load_model`, the run's first MLX allocation (the decode is PyAV and torch only). Not at module scope, which AppTest and every rerun re-execute. `test_run_caps_the_mlx_cache_before_loading_the_model` pins the order against the speech loader by patching the shared `mlx.core.set_cache_limit`, and that it is called once across two runs; the measurement is under Performance
- `load_model` — cached speech-model loader: `mlx_audio.stt.utils.load_model(model_id, revision=revision, strict=True)`, called with `MODEL_ID` and `MODEL_REVISION` (`revision` travels through the loader's `**kwargs`). **`strict=True` is deliberate and the opposite of `mlx_audio`'s default.** `strict=False` leaves any weight the checkpoint fails to supply randomly initialised, and greedy CTC would still decode — into confident nonsense, with no error anywhere. That is exactly the failure mode the VAD loader documents and *cannot* guard against, because its checkpoint legitimately omits the `vad_8k.*` keys; this one is IBM's own bf16 checkpoint, loaded directly with no community conversion in between, and it ships every key — so a missing one can only be a renamed key upstream (in the port's `sanitize`, or in the repo), and that is an error worth raising at load time rather than a transcript worth debugging later. The revision is pinned even though the repo is org-maintained and loads strictly: strict proves every key is *present*, not that the weights are the ones the constants in this file were measured against, and a retrained checkpoint pushed to main would decode without complaint into different transcripts on the next cold cache. The hash is what makes a transcript reproducible. (The port's `post_load_hook` reads `tokenizer.json` from the snapshot, so a `FileNotFoundError` from there is a broken snapshot, not app code.)
- `_open_container` — the one `av.open` call site for uploads (`mode="r"`). `av.open` decodes container *and* stream tag text to `str` at open time, and FFmpeg's wav demuxer copies RIFF INFO / BWF `bext` text in byte for byte (only ID3 is transcoded). PyAV 18 decoded strictly by default, so an ANSI artist tag from a Windows/DAW tool raised `UnicodeDecodeError` on a perfectly decodable file — and because that is a `ValueError`, `audio_duration_seconds` swallowed it into a silent `None`; the helper passed `metadata_errors="replace"` to stop it. PyAV 19 removed that keyword (passing it is a `TypeError`) and always decodes tags as UTF-8 with `"surrogateescape"`, which cannot raise, so the `av>=19.0.0` floor is what now holds the fix and `latin1_tagged_wav` still pins it. One helper so the two opens cannot drift apart. (av 19's stubs also type `Stream.codec_context` as non-optional, so an editor running ty may grey out `_decode_audio`'s `codec_context is None` branch as unreachable; it is not — `undecodable_mkv` takes it)
- `_best_audio_stream` — `container.streams.best("audio")` narrowed by `isinstance` to `av.AudioStream | None` (`best()` is typed `Stream | None`). That is `av_find_best_stream` — the track flagged `default`, then the higher-bitrate / more-frames one — i.e. the same pick the torchcodec path made, so a multi-track mp4/mkv keeps transcribing the track it always did. **Not** `streams.audio[0]`: that is the lowest-indexed track, which on a file whose commentary or low-bitrate track comes first is silently the wrong one, with the duration gate reading that track's length too
- `_decode_audio` — PyAV decode of the best audio stream (`_best_audio_stream`) to `(channels, samples)` float32 at the native rate. Every frame goes through an `av.AudioResampler(format="fltp", layout=..., rate=...)` first, built from the **first decoded frame's** layout and rate rather than the stream header's: the two normally agree, but HE-AAC with implicit SBR declares half the rate its frames carry, and a converter targeting the header's rate would have swresample downsample every frame to it and report the wrong rate to the resample that follows (the header only serves the zero-frame return). With layout and rate unchanged the conversion is a pure sample-format one (swresample buffers nothing), so packed and planar codecs, `s16` and `fltp` alike, all concatenate into the same matrix scaled to [-1, 1] — the scaling torchaudio applied, hence bit-exact on 16-bit PCM, and verified identical to the old torchcodec output on both fixtures including the AAC-in-mp4. Raises `ValueError` on a container with no audio stream, and on a track whose codec the bundled FFmpeg cannot decode (PyAV leaves `codec_context` `None` there, and `AudioStream.__getattr__` would otherwise surface it as `'AudioStream' object has no attribute 'layout'`) — both of which the caller turns into the `RuntimeError`
- `load_and_preprocess_audio` — `_decode_audio` on the upload's bytes, downmixes to mono, resamples to `SAMPLE_RATE` (16 kHz) with `torchaudio.functional.resample`; raises `RuntimeError` on failure, including a zero-sample decode and — **after** the resample — anything under `MIN_AUDIO_SAMPLES = 1120` (70 ms at 16 kHz). Both guards belong here rather than downstream: an empty or too-short waveform passes VAD (which falls back to a full-audio segment) and only dies inside the port as a `ValueError` — `audio must contain at least one 10 ms frame` under 160 samples, then an STFT `Input is too short`, a `[reshape]` error from 172, and an opaque `[conv]` shape error from 225 up to 1119 (swept every count from 160 to 1120: 1119 fails, 1120 decodes; the encoder needs 4 stacked mel frames through two stride-2 subsampling blocks and a kernel-7 depthwise conv) — which the UI would surface as an `st.exception` traceback where a `RuntimeError` gets the one-line `st.error`. They are two checks, not one, because the zero check must run *before* the resample (`torchaudio.functional.resample` raises its own opaque reshape `RuntimeError` on an empty tensor at any rate but 16 kHz) while the floor must be measured in the model's samples *after* it (3000 samples at 48 kHz is 1000 here). Segments never trip the floor — VAD buffering makes each at least 0.6 s and `_split_long_segment` parts are ≥ `MIN_SEGMENT_DURATION_S` — so it only ever fires on a whole clip, typically a mis-click on **Record**
- `transcribe_audio` — `model.generate(audio=wav.squeeze().numpy()).text`: one encoder pass and a greedy CTC collapse over a waveform slice. There is no prompt, no token budget and no autoregressive loop — `generate()` takes only the audio (keyword-only `verbose`/`generation_stream`, and `**kwargs` that are **silently ignored**, so a stray `max_tokens=` would be dropped, not rejected) and returns an `STTOutput` whose `.text` is already `.strip()`ped, with `.segments == []` (no word timestamps; the app's timestamps come from VAD) and `.language == "en"`. Output is lowercase and unpunctuated, the way the model's training transcripts were normalised
- **Transcript analysis** (`docs/PLAN.md` Phases 1 and 2: code in B5–B6, UI in B7; what it looks like is under UI Layout, Analysis): with the constants it measured — `LLM_ID`/`LLM_REVISION` (Granite 4.2 3B q8, chosen at B4), `MAX_ANALYSIS_TOKENS = 24_576`, `ANALYSIS_TOKENS_PER_WORD = 1.072`, `ANALYSIS_MAX_NEW_TOKENS = 512`, `ANALYSIS_PREFILL_TOKENS = 2048`, `ANALYSIS_PROGRESS_TOKENS = 32` — and the prompt the evaluation chose (`ANALYSIS_SYSTEM_PROMPT`, `ANALYSIS_TRANSCRIPT_PROMPT`, `SUMMARY_PROMPT`, `SUMMARY_RETRY_PROMPT`; plus `QUESTION_PROMPT`, the evaluation's `anyone` wording; the evaluation runs these, so a wording change is a change to what was scored — re-run it).
  - `load_llm` — `@st.cache_resource`, `_load_llm(model_id, revision=revision)` and nothing else: no `strict=` because `mlx_lm.load` has none (its `load_model` defaults to strict, pinned by contract test), and `trust_remote_code` left at `False`. `LocalEntryNotFoundError` (offline, Hub unreachable) → `RuntimeError("The language model isn't downloaded yet, …")`; a full disk → `RuntimeError("Not enough disk space … (about 4 GB) to <HF_HUB_CACHE>.")`, detected by `ENOSPC` **or** the OS text, because `hf_xet` raises a bare `RuntimeError` (Phase 0); anything else propagates unchanged
  - `check_analysis_length` — the word-count pre-check, before the model loads: refuses above 1.2 × `MAX_ANALYSIS_TOKENS` estimated tokens
  - `prefill_transcript` → `TranscriptPrefill(cache, ids, messages)` — the system turn plus the transcript turn, through `apply_chat_template(..., enable_thinking=False)`, prefilled once in 2048-token chunks with `on_progress(i, n, "part i+1 of n")` **before** each. Refuses over `MAX_ANALYSIS_TOKENS` with the exact count, never truncates. `messages` travel with the cache because every task builds its prompt as those turns plus its own
  - `_task_cache` — the prefix check: the task's full prompt must start with the cached ids; if a template rewrote them, a fresh cache, the full prompt and a `RuntimeWarning` carrying no transcript text
  - `summarize_transcript` — greedy `generate_step` from the shared cache, stopping on `tokenizer.eos_token_ids` itself (`generate_step` has no EOS check), `on_progress(n, ANALYSIS_MAX_NEW_TOKENS, "summary")` every 32 tokens, a "cut off" `RuntimeError` with **no** retry on running out of tokens, and the trim back to the prefix by `cache[0].offset - len(ids)` in a `finally`, so success, failure and retry all leave the cache at the prefix. One retry on unparseable output, showing the bad reply back; then `RuntimeError`. `parse_summary` takes the outermost braces (so a fence or prose around the object is fine), `json.loads` only, and raises `ValueError` (no object) or `TypeError` (wrong keys or types)
  - `segments_text` — the segments' texts joined, the analysis input
  - `DEFAULT_QUESTIONS` — the nine the evaluation labelled; `tests/test_evals.py` keeps them equal to `labels.json`'s. `MAX_QUESTIONS = 20`, `MAX_QUESTION_CHARS = 200`
  - `clean_questions` → `CleanedQuestions(questions, too_long, special, over_limit)` — one per line, blanks and repeats dropped, then lines over 200 characters, lines containing `<|` (the tokenizer would make special-token text in a question into real control tokens), and anything past 20. The counts feed the captions under the questions box
  - `_yes_no_ids` — `Yes`/`No` with no leading space (what follows `<think></think>`), each required to be one token, else `RuntimeError`

It was icon-only until the review; `type` stays at the default rather than `"tertiary"`, since a bordered button is the Carbon identity the theme sets with `showWidgetBorder`. `on_click="ignore"` because nothing reads the click either: the result is already in session state, so the default rerun does no work the app wants — then `st.text(transcript)`. The download is in the header rather than under the text because a 20-minute transcript is ~200 lines, and a button below it was the only action on the page and a few hundred lines below the fold
- `run_pipeline` — `(wav, model, vad_model=None, on_progress=None, use_segmentation=True) -> PipelineResult`: a **single** result, not a dict keyed by task. When segmentation is on it asserts `vad_model` and runs `get_speech_segments`; when off it treats the full audio as one `[0, duration]` segment. Segments only — one `transcribe_audio` per segment, each emitted as `[M:SS - M:SS] text` and joined with newlines into `transcript`, and also kept untimestamped in `segments` (`list[Segment]`, `{start, end, text}`), which is what the analysis reads. `on_progress` contract, exactly: `(i, total, f"segment {i + 1} of {total}")` **before** each segment, with `total = max(len(segments), 1)`, and nothing else. There is deliberately no closing `(total, total)` call: it existed to hold the bar at full during the guardian pass, and with nothing running after the last segment it would fire microseconds before `main()`'s `finally: progress.empty()`, be coalesced with it in the same flush, and in practice never paint. On the fixture the calls are `[(0, 1, "segment 1 of 1")]`.

  There is no encoder hoist any more, and nothing to replace it with. The 4.1 model was a conformer encoder feeding a 2B LLM decoder, so a segment's encode (~33% of a call, and prompt-independent) could be computed once and shared across N task prompts — `_supports_encoder_hoist` / `_encode_segment` / `_generate_from_features` reached into five `mlx_audio` internals plus `mlx_lm.generate.generate_step` to do that, measured 28% faster on 4 tasks × 5 segments, and carried a name probe, a `try/except` drift fallback and a `RuntimeWarning` to survive upstream renames. With TurboCTC the encode **is** the whole call: one encoder pass, an `argmax`, a CTC collapse and a tokenizer decode, with no prompt, no decoder loop, and only ever one output per segment — so there is nothing to amortise one encode across. The speech model is now driven purely through `mlx_audio`'s public `generate()`, the speech path imports nothing from `mlx_lm` (the transcript analysis does, for its own model — see Dependencies), and `_supports_mlx_vad` is the only remaining probe over `mlx_audio` internals. Don't reintroduce a hoist: it would buy nothing and reopen a private surface.

### Models

- [Granite Speech 5.0 470M TurboCTC](https://huggingface.co/ibm-granite/granite-speech-5.0-470m-turboctc) — English transcription (MLX, bf16). **IBM's own repo**, loaded directly by `mlx_audio`'s `granite_speech5_ctc` port with no community conversion in between, pinned to `2864561` (`MODEL_REVISION = "286456107c8ba1161f5c22dfe85466402c88333b"`). Encoder-only: 16 conformer blocks with 128-frame block-local attention (relative positions only within a block), pyramidal 8× temporal subsampling from the 100 Hz mel frames to 12.5 Hz (2× frame stacking, then stride-2 convolutions in blocks 0 and 1), self-conditioned CTC at the midpoint (after block 8 of 16, tied to the final CTC head), and a 16,384-unit BPE vocabulary; greedy CTC decoding, no prompt, no decoder. Apache 2.0. English only; output is lowercase and unpunctuated. Paper: [arXiv 2609.20104](https://arxiv.org/abs/2609.20104), "Design of the IBM Granite 5.0 TurboCTC ASR Model". **Note the `-nc` sibling** (`granite-speech-5.0-470m-turboctc-nc`) is CC-BY-NC-SA 4.0, research and non-commercial only, and is *not* the one loaded. Replaced the `divydeep/granite-speech-4.1-2b-mlx-8bit` community conversion of the 2B encoder+LLM model, which is what carried translation, source languages and keyword biasing

ChatML template, driven with `enable_thinking=False`; `Yes` 9642, `No` 2822, EOS `<|im_end|>` 100257, all single tokens. Greedy decoding on purpose — `generation_config.json`'s temperature 1.0 is not read by `mlx-lm`, and a summary that changes between identical runs is not useful. Apache 2.0. Chosen over `ibm-granite/granite-4.2-8b-q4-mlx` at B4 on measurement (see the evaluation section below): 3–4 points lower ROC-AUC on ASR transcripts, twice as fast, and the only candidate inside every budget

Ships 16 kHz only — no 8 kHz branch
- [Silero VAD](https://github.com/snakers4/silero-vad) — the PyTorch build of the same checkpoint, kept as the fallback path (runs on CPU). Note `mlx-community/silero-vad` (no suffix) is the older **v5** line, a genuinely different checkpoint, not a variant of this one

**Moving a pin cleans up after itself.** A pinned revision never deletes the snapshot it replaced, so whenever `MODEL_REVISION`, `MLX_VAD_REVISION` or `LLM_REVISION` changes, delete the old revision from the HF cache in the same session, once the new one has loaded and its tests pass: `uv run hf cache rm <bare revision hash> --dry-run`, then without `--dry-run`. Neither the dry run's total nor the real run's "Saved …" is the space freed — only files no remaining revision uses are deleted, and the report counts shared and never-downloaded files too (on 2026-10-17 it claimed 9.3 GB for two entries that freed ~7 MB) — so measure with `du` on the whole `hub/` before and after. Then `hf cache verify <repo> --revision <hash>`; for TurboCTC its warning about 3 remote files missing locally (`model.sig`, `README.md`, `.gitattributes`) is expected, since `mlx_audio` fetches only what it loads

### Languages

English transcription only. Granite Speech 5.0 TurboCTC is an English ASR model with no prompt and no decoder, so there is no source-language selector, no translation and no keyword biasing, and the output carries no casing or punctuation (its training transcripts were normalised to lowercase, unpunctuated text; the app does not restore either). The analysis inherits that shape: its prompt tells the 3B the transcript is lowercase, unpunctuated ASR output that may contain misheard words, and a misheard word can still surface in a summary. Its prompts and evaluation are English too; the length limit (`MAX_ANALYSIS_TOKENS = 24_576`, about two hours of meeting speech) and the memory and speed it was set from are in the two Transcript analysis sections below.

Known model behaviour — the measurements that set the segment cap and floor (this machine, mlx-audio 0.5.4, greedy CTC on the pinned revision):

- **No length cliff.** Attention is block-local — 128 frames per block at 12.5 Hz (10.24 s), relative positions only within a block — so there is no context length to run out of. One hour of tiled speech transcribed in a single pass with no drift: 357 of 360 repetitions detected, the misses at the artificial tile seams. The old model's "past ~20s it echoes the source language" cliff was an LLM-decoder behaviour and is gone with it.
- **Memory is linear** in clip length, ≈2 MB per second of audio over the 0.88 GB resident base (fresh process per run): 10s → 1.13 GB, 30s → 1.45, 60s → 1.66, 120s → 1.80, 300s → 2.02, 600s → 2.50, 1200s → 3.43, 1800s → 4.53, 3600s → 7.83 GB. That series is MLX alone, and it is *not* what sets `MAX_VAD_OFF_DURATION_S = 1800` on its own: the Streamlit process also holds the PyAV decode at the **source** rate and channel count (a 48 kHz stereo hour is ~1.4 GB float32 before the mono and 16 kHz copies), the upload bytes and the torch baseline — so a single-pass hour lands past 10 GB in-process and swaps a 16 GB Mac, where 30 minutes keeps the whole process around 7 GB. Both process figures include the since-removed guardian (125M fp32 parameters, ~500 MB — the `transformers` import itself stays: `mlx_audio.stt.models` imports the `granite_speech_nar` port, which imports `AutoTokenizer` at module scope, so every speech-model load pulls it in), so they err high — the safe direction for a ceiling. With VAD on there is no ceiling at all.
- **Forced splits cost a little.** WER with equal-length parts and mid-utterance cuts: 73 LibriSpeech dev-clean utterances (1150 words) — **whole 6.17%**, 10 s parts 6.52%, 5 s parts 8.17%; longer utterances had *lower* WER (15–20 s bucket 2.6%), and hypothesis/reference word counts matched. 64 s of continuous TTS speech (198 words) — **whole 8.59%**, 60 s cap 9.09%, 30 s cap 9.09%, 15 s cap 10.10%, 8 s cap 8.59%; through the app's own VAD path, 30 s cap 9.60% (3 segments) vs 8 s cap 10.61% (10 segments). So the cap exists for timestamp readability, not accuracy, and every split is a small cost — hence `MAX_SEGMENT_DURATION_S = 30.0` (about three 128-frame attention blocks, so a forced part never sees less than a full block of context) and `MIN_SEGMENT_DURATION_S = 20.0` (above half the cap, so a span only modestly over it stays whole rather than halving; see `_split_long_segment`). With VAD **off** no cap applies and the whole clip is one inference, which this model handles up to the memory ceiling above — that path just loses the timestamps.

Fixture quirk worth knowing before touching the real-weights test: `tests/data/audio/sample_10s.wav` opens with 0.76 s of exact digital-zero silence. On the **whole clip** (VAD off) the model returns `shapeare on scenery by oscar wilde public` — it drops the second sentence ("this is a librivox recording all librivox recordings are in the public domain"). Through the app's **VAD path**, which trims the lead-in, it returns `shakespeare on scenery by oscar wilde a librivox all librivox recordings are in the public domain` as one segment `[0:00 - 0:09]` (buffered 0.76–9.99 s). (On mlx 0.32.2 that segment read `a libvox`; mlx 0.32.4 alone flipped it — same waveform, same VAD span, same port code — a bf16 numerics change that happens to land on the right word.) The reference `transformers` implementation (resolved transitively via `mlx-audio` — nothing here imports `transformers` directly; first compared on 5.17.0, re-run on 5.20.2 in bf16 on 2026-10-20 after the mlx change, where it too returns `a librivox` and the same whole-clip string) produces byte-identical output to the MLX port on every clip tried, this one included, so it is the model's behaviour, not the port's; on normal audio (LibriSpeech) word counts match, so it is fixture-specific rather than a general dropped-sentence problem.

Before it, the bar was created inside the `if run_clicked` branch, so it held index 0 on the run's own rerun and nothing held it afterwards: the card sat at index 1 and then at index 0 on the next rerun, and a changed delta path remounts it (measured with `AppTest`: `[(0, 'empty'), (1, 'flex_container')]` → `[(0, 'flex_container')]`). Popping up front makes a failed run leave nothing behind, and the happy path is unchanged since success overwrites both keys. `test_a_failed_rerun_does_not_leave_the_previous_card` drives it, injecting the failure on the model rather than on `run_pipeline` (a `streamlit_app` attribute patch does not cross AppTest's boundary). (`on_progress` fires *before* each unit of work, so the label names what is in flight rather than what just finished; the bar therefore never reaches full — it is emptied, not completed, and a closing call would be coalesced with the `empty()` and in practice not painted — see `run_pipeline` above.)

The analysis slot then shows an `st.skeleton` sized from measurements — `ANALYSIS_SUMMARY_HEIGHT_PX = 660` plus `BOARD_ROW_HEIGHT_PX = 51` per question and a caption line — which cut the transcript card's jump when the real card lands from 457 px to 45 px (the progress bar above going away). `check_analysis_length` runs before the model loads, so a hopeless length never waits behind a 3.9 GB download; then "Loading language model..." (`show_time=True`; a cold fetch took 110 s in B3) and the `feedback` bar through "Reading transcript (part i of n)...", "Summarising..." and "Answering question i of n...", each update a point where a rerun can stop the run. A blank transcript is never analysed ("No speech to analyse."; summarising nothing would only invent content). `_analysis_section` is the slot's own error boundary — `RuntimeError` → `st.error(str(e), icon=":material/error:")`, anything else → `st.exception`, both inside the slot, neither returning from `main()` — and success fires `st.toast("Analysis complete", icon=":material/check_circle:")`, the card adding no `st.success` banner, matching the transcript's
- **Analysis card** — `_render_analysis_card`, a bordered card laid out like the transcript's: a header row with `st.subheader("Analysis")` and a `"Download"` button for `<stem>_analysis.md` (`text/markdown`, `key="dl_md"`, `help="Download analysis"`, `on_click="ignore"`), then fixed bold labels — **Topic**, **Summary**, **Key topics**, **Action items**, **Questions** — each followed by the model's field through **`st.text`, never `st.markdown`**: a transcript can carry spoken instructions, and a Markdown image in a summary would make the browser fetch a URL with no click, sending transcript text out of an offline app. Topics are joined with ` · `, action items are `• ` lines, and an empty list reads "None." as a caption. The Markdown download escapes every field (`_escape_markdown`), the questions too, since a `|` would split a table row. There are no confidence numbers on generated fields: a number the LLM writes is made up, not measured
- **Question board** — under **Questions**, `_render_board`: one `st.progress` per question, **sorted by P(yes), highest first** (stable, so ties keep the user's order), labelled `**0.87** · question` — the number first, so the scores line up down the left edge and the value never rests on bar length or colour alone — then `st.caption(BOARD_CAPTION)`, "Sorted by P(yes), highest first. Scores rank the questions; they aren't verdicts." So the dataframe theme keys were never added to `config.toml`. Measured card height with the nine defaults: 1148 px at 1470 px (sidebar open), 1419 at 1024, 1248 at 760, 1072 from 1920 up
- **Analysis invalidation** — `summary` is keyed by `_last_input_key` alone and `board` by `_board_key = (_last_input_key, questions)`, so editing a question drops the board but never the summary, the slow part (`test_editing_questions_rescores_the_board_only`). All five result keys (`_RESULT_KEYS`: `result`, `result_stem`, `summary`, `board`, `_board_key`) are popped together when the input changes and at the top of every Transcribe. Turning analysis on, or editing questions, **after** a transcript exists never re-transcribes: the slot shows a secondary "Analyse" button (`:material/summarize:`, wired through an `on_click` callback because the click has to be known before its own slot is drawn) — or, with a summary present and the board stale, "Press Analyse to score these questions." above it — and `run_analysis` computes only what is missing, from one prefill. Zero questions after cleaning show "Add at least one question to score." in the board's place. Nothing about the transcript's KV cache is kept between reruns (B4: 0.5 GB per tab at 30 minutes, 2 GB at the cap), so a board-only re-run pays one prefill — 1.8–1.9 s on a 2:17 meeting, and at 30 minutes 13.2 s of prefill plus ~2 s of questions
- **One inference at a time** — `inference_lock`, a process-wide `threading.Lock` behind `@st.cache_resource`, held around `run_pipeline` and the analysis (each tab is its own script thread sharing the cached models; two analyses would hold two KV caches and drive one MLX model from two threads, which is untested), **never around a model load**, so a first-use download cannot stall every other tab. `_inference_turn` waits in 0.5 s polls, each painting "Waiting for another run to finish..." on the bar — an `st.*` call, so a waiting run can be stopped — and releases in a `finally`, since Streamlit's stop is a `BaseException`
- **Session only, on purpose** — `result`, `result_stem`, `summary`, `board` and `_board_key` live in `st.session_state` and are lost on a browser refresh, like the transcript always was; edited questions reset to `DEFAULT_QUESTIONS` in each new session. That is the app's design of writing no user data to disk, not an omission: the two download buttons are the only exports, and keeping results or question sets between sessions (with SQLite, per `docs/PLAN.md`, Out of scope) would be its own feature

### Performance

- Speech model runs via MLX on Apple Silicon GPU (bf16, 0.88 GB resident). ~380–480× realtime after warm-up on M-series: 20 min of audio in 2.55 s, 1 h in 10.2 s. Peak MLX memory is linear in clip length at ≈2 MB per second of audio — 1.13 GB at 10 s, 1.66 GB at 60 s, 3.43 GB at 20 min, 7.83 GB at 1 h (full series under Languages) — so a 30 s segment under VAD peaks around 1.45 GB
- One encoder pass per segment is the entire inference cost — there is no decoder loop and nothing to hoist (see `run_pipeline`)
- Deferred model loading — speech and VAD models load on first pipeline run, not on page load; the analysis model on the first analysis, never while the toggle is off
- `@st.cache_resource` to cache models
- No torch decorator on `run_pipeline` — the PyTorch VAD fallback's `get_speech_timestamps` is `@torch.no_grad()` itself, and nothing else in the pipeline touches autograd
- `io.BytesIO` for in-memory audio loading (no temp files)
- Audio downmixed to mono and resampled to `SAMPLE_RATE = 16000` Hz on load
- `audio_duration_seconds` cached in a single `st.session_state["_duration"]` slot holding `(file_id, duration)` so `av.open` doesn't re-parse the container headers on every rerun; the slot is overwritten when the file changes, so it can't grow unbounded (no eviction needed). **Not** to avoid a buffer copy, which is what this bullet used to claim: `UploadedFile.getvalue()` is O(1) on an unmodified upload — CPython's `BytesIO` hands back the same `bytes` object, the copy-on-write `UploadedFile.__init__` cites in its own comment (measured: `v is b` at 200 MB). `getbuffer()` is the call that would force the unshare, so don't reach for it
- Silero VAD runs on the Apple GPU via MLX (~1.2 MB of weights, 309K params); encoder batched across chunks then one LSTM pass, ~3x faster than the PyTorch path and identical in output. `VAD_ENCODER_BATCH_CHUNKS = 2048` bounds peak memory (+43 MB over streaming on 15 min of audio). Falls back to PyTorch CPU on any drift
- **MLX's buffer cache is capped at `MLX_CACHE_LIMIT_BYTES = 1 << 30` (1 GiB)**, by `limit_mlx_cache`, because without a cap the cache — not the models — set the peak on long audio. Uncapped, a 30-minute VAD transcription left MLX holding 0.88 GB active and **6.39 GB** of freed buffers in its cache (6.62 GB at 1 h), a 7.76 GB footprint in the Phase 0 spike. Re-measured through the real app for A7 (2026-10-21; Streamlit server `phys_footprint`, 32 minutes of synthesised meeting speech uploaded and transcribed with VAD on via Playwright, fresh server per run, two runs per configuration): **8.47 GB** after the run without the limit (lifetime peak 8.66 GB), **2.48–2.49 GB** with it (lifetime peak 3.27 GB), transcript byte-identical across all four runs, click-to-card 12.9 s in both configurations on the second runs. The analysis depends on it: the whole-process budget of ~10 GB with both models resident was met only under the limit in Phase 0 (8.53 vs 11.87 GB at 30 minutes, on the 8B), and the shipped 3B's peaks — 7.71 GB at 32 minutes, ≈ 9.2 GB at `MAX_ANALYSIS_TOKENS` — were all measured under it (see the two sections below)

That is ~50% of the M2 Pro GPU's fp16 ceiling for 8B parameters, so neither `kv_bits` nor chunking can help: 30 min prefills in ~30 s, 1 h (12,458 tokens) in ~67 s

- **Whole process, speech model and LLM both resident, 30 min** (transcribe, then load, prefill, summary, 10 questions): **11.87 GB** peak with no cache management; **9.88 GB** with `mx.clear_cache()` before the LLM loads (the cache refills to 2.7 GB during prefill); **8.53 GB** with `mx.set_cache_limit(1 GiB)`, same speed. At 1 h: 11.96 GB with `clear_cache` alone, **9.68 GB** under the limit. Under the limit the peak runs ≈ 6.2 GB + 0.28 MB/token, reaching 10 GB near 14K tokens
- **Torch's share:** 140 MB of footprint for `import torch, torchaudio`, +4 MB for `load_silero_vad()`; all of `streamlit_app` imports to 188 MB. Under 2% of the analysis peak
- **Yes/No readout:** `Yes`/`No` are the top two next tokens on all 40 prompts tried (4 transcripts × 10 questions); Yes+No mass min 0.954, median 0.994; the runner-up is `Based`
- **Cache equivalence.** Cached prefix + suffix vs the full prompt from scratch: max |Δlogit| 0.28–0.50, P(yes) within 0.008, argmax identical — bf16 rounding from running the suffix as its own forward pass (fresh-chunked and unchunked agree exactly), so equivalence tests need a tolerance, not equality. `trim_prompt_cache` is **exact** (max |Δ| 0.0), after a question and after a summary. After a summary `cache[0].offset` is one past what the loop consumed (3038 vs 3037), and `trim(offset - len(prefix))` lands exactly on `len(prefix)`

The hand-written chunk loop stays

### Tests

`tests/test_streamlit_app.py` — unit tests over the helpers, model loaders, audio loading, transcription, pipeline execution and result-card rendering, with `st` mocked wholesale. `grep "def test_"` is the coverage inventory, so what follows is only the conventions and the invariants worth not breaking. `TestGraniteSpeech5Contract` exercises the genuinely installed `mlx_audio` surface the speech path relies on, since everywhere else the model is a `spec=["generate"]` mock and an upstream change would ship green. The app reaches into no private speech-model internals any more, so this is the whole contract, one registry check, two signature checks and one smoke test: `"granite_speech5_ctc"` is in `mlx_audio.stt.utils.MODEL_REMAPPING` (what the `>=0.5.1` floor in `pyproject.toml` promises — absent in 0.5.0 and 0.4.x, where the load fails with an unsupported-model error rather than an `ImportError`); the port's `Model.generate` has an `audio` parameter *and* a `**kwargs` (which is why `TestTranscribeAudio` pins the kwargs set — the model would never object to a stray one); and `mlx_audio.stt.utils.load_model` has `strict` as a **named** parameter rather than something that would fall into its `**kwargs` and be forwarded or dropped silently, quietly restoring the non-strict default. `test_transcribes_the_fixture_with_real_weights` then loads `MODEL_ID` at `MODEL_REVISION` through `_load_model`, runs `sample_10s.wav` through `load_and_preprocess_audio` and `transcribe_audio` — the whole clip, no VAD — and asserts only that the text is non-empty, equals its own `.lower()`, and contains `oscar wilde`. It runs **only where the pinned snapshot is already in the local HF cache** (gated on `huggingface_hub.try_to_load_from_cache(MODEL_ID, "model.safetensors", revision=MODEL_REVISION)` returning a path, which with a full commit hash never touches the network) and `pytest.skip`s otherwise — CI included. That gate is not the try/except-skip pattern `test_both_backends_agree_on_real_audio` uses, on purpose: `mlx_audio`'s loader calls `snapshot_download` on a cache miss and does *not* raise, so on a networked runner the load would *succeed* by fetching 0.95 GB per matrix leg per run. The try/except around the load stays for the other case, a cached snapshot that no longer loads. **Do not tighten that assertion to the full sentence.** On the whole clip the model returns `shapeare on scenery by oscar wilde public` — the second sentence dropped, the first word misread — and the reference `transformers` implementation returns the byte-identical string, so this is the model's behaviour on this fixture (the digital-zero lead-in, see Languages), not the port's. Pinning the exact text would pin a quirk: a retrained checkpoint that *fixes* it would then fail the test for getting the transcript right, and the VAD path already yields a different string from the same clip. Greedy CTC on a pinned revision is deterministic, so the assertions are stable; `oscar wilde` is what every path — whole clip, VAD path, reference implementation — agrees on, and lowercase is the one output property the model guarantees.

`TestMlxVadInternals` is the VAD equivalent, and exists for the same reason: everywhere else `_mlx_vad_probabilities` is mocked, so without it the code driving `mlx_audio`'s branch submodules never runs in CI. It builds a **real** `mlx_audio` `Model` from a real `ModelConfig` with random weights — no download, but real classes, real shapes, and a real streaming implementation (`_predict_proba_array`) to check the batched one against. Two tests assert that equivalence: one at the default batch size, and one with `VAD_ENCODER_BATCH_CHUNKS` patched to 4, which is the only way the `(hidden, cell)` handoff across batches gets exercised — drop the carry and a single-batch test still passes. A third builds a `Model` with `hop_length=64` and asserts `_mlx_vad_probabilities` **raises** rather than dropping frames. `test_both_backends_agree_on_real_audio` then runs real weights on `sample_10s.wav` through both backends and demands identical spans; it `pytest.skip`s (not fails) when the repo cannot be fetched, so an offline CI run does not go red over a network absence. Pinning `MLX_VAD_REVISION` froze one side of that pair and `silero-vad==6.2.1` freezes the other (see Dependencies), so while both pins stand the test is a tripwire for the pins themselves; it becomes load-bearing again the moment the silero-vad pin is lifted, when a `uv lock` could bump it to a future Silero release and leave the backends disagreeing with nothing else to notice.

`make_mlx_vad_model(drop=...)` builds a spec'd stand-in for the MLX model with any one probed name removed — `spec=` throughout, since a bare `MagicMock` conjures every attribute the probe asks for and would never report drift. `TestSupportsMlxVad` parametrizes it over all 19 probed names, plus two cases asserting a mismatched `chunk_size`/`context_size` is refused by value; `TestSileroVadDispatch` covers the four routing outcomes (torch model → torch, MLX model → batched, non-16 kHz → torch regardless, MLX raising → warn + torch). `TestSileroVad` now passes `MagicMock(spec=torch.nn.Module)`, since a bare mock no longer routes to the PyTorch path.

Durations are faked through the `_header_duration` helper, which patches the shared `av.open` with a stream carrying `duration` in a `Fraction(1, 16000)` time base — so the app's `duration * time_base` arithmetic runs rather than being bypassed — since no fixture is half an hour long; the Run tests bound the VAD segment against the fixture's frame count read with the stdlib `wave` module, not with the decoder under test. AppTest re-executes `streamlit_app.py` in a fresh namespace on every `.run()`, so mocks must patch the **shared upstream imports** (`mlx_audio.stt.utils.load_model` for inference, `mlx_audio.vad.utils.load_model` for VAD, `av.open` for header-only duration reads) rather than `streamlit_app.*` — patching `streamlit_app` attributes does not cross AppTest's script-runner boundary, and clicking Run without an upstream patch would fetch the real ~0.9 GB speech model and the MLX VAD checkpoint from the Hub. Session-state assertions go through the 1.64.0 `_AppTestSessionState` wrapper (streamlit#16897): `in`, iteration and the dict methods serve `filtered_state` — user keys plus keyed widgets; a leading underscore such as `_duration` is *not* internal, only the `$$STREAMLIT_INTERNAL_KEY` prefix is — while `[]`, attribute access and `get()` reach the raw state. There is no `.filtered_state` attribute on it any more (it falls through `__getattr__` to an `AttributeError`), so membership is spelled `"result" not in at.session_state` and the single-slot check iterates `at.session_state` for every key starting with `_duration` (a per-upload `_duration_<file_id>` key would show up there); that iteration is the one line that needs the `dev` group's `streamlit>=1.64.0` floor. The Run tests are hermetic: the `speech_loader` fixture patches the MLX loader to return a `MagicMock(spec=["generate"])` whose `generate` yields `"hello world"`; `load_model` calls it as `(MODEL_ID, revision=MODEL_REVISION, strict=True)` — every Run pins that with **`assert_called_once_with`** — so the mock must accept `strict=True` by keyword, and a stand-in with a narrower signature would raise inside the script runner and surface as an exception element rather than a card. `_offline_mlx_vad()` makes the MLX VAD loader raise `OSError("offline")` so `load_vad_model` takes its documented fallback onto the PyTorch build inside the `silero-vad` wheel — real VAD spans on the fixture (the one segment is asserted shorter than the clip, since VAD trims the 0.76 s lead-in, and the line still reads `[0:00 - 0:09] hello world`), nothing downloaded, and the `RuntimeWarning` asserted with `pytest.warns(..., match="using the PyTorch VAD")`. An autouse fixture clears `st.cache_resource` before each test, since AppTest does not reset Streamlit's resource cache between instances. Pure-UI cases avoid clicking Run entirely. The one **failing** Run is `test_undecodable_upload_shows_a_readable_error`: nine bytes of non-audio through the real decoder, asserting the one-line `st.error` with its `:material/error:` icon lands in the transcript column, `at.get("progress")` is empty (the `finally`), and there is no toast, no card and no `result` — plus that `speech_loader` was **never called**, which is the assertion that pins the decode-before-model-load ordering, the thing that keeps a file that was never going to decode from waiting behind a ~0.95 GB fetch. Every `.run()` that then reads an element or session state is preceded by `assert not at.exception`: `AppTest._run` does not raise on a script crash, it appends an `exception` element, so without the check a crash surfaces as a `ValueError` from an unpack or a `KeyError` from the slot instead of the traceback that would say what broke.

The two `config.toml` guards are both written to outlive the config they were added for. `test_config_theme_defines_both_palettes` asserts *conditionally* — `if "theme" in app_config` — so dropping the theme altogether stays a valid state rather than a failing one, and while a theme is shipped it enforces the both-sub-palettes rule above, which is the regression it actually exists to catch — by value, not just by header, since an empty `[theme.light]` sets nothing and collapses the menu just the same. It does not pin any colour: the palette is reviewed by eye and by ratio, not by test, so a retune of one value is a config change, not a test change. `test_config_has_no_invalid_options` checks every key against `config._config_options_template` because Streamlit **drops unknown options with only a server-log warning** instead of rejecting them, so a typo'd `maxUploadSize` would cost 500 MB uploads with nothing on screen to say so. Its `_option_paths` helper is module-level and separately parametrized: every key the shipped file sets is a registered leaf, so the file exercises only that branch, and the shapes that would break the walk are pinned by synthetic tables instead — an option whose *value* is a table (`server.trustedUserHeaders`) or an array of tables (`[[theme.fontFaces]]`) must terminate the walk, since descending into free-form inner keys fails a valid config, while a typo under an unregistered prefix and an empty typo'd section header must still be reported.
